# Agent Guidelines for FF-WebHID

Before you act, read `CONTRIBUTING.md` for the project's design principles. They apply to you too.

This file holds agent-specific context: historical gotchas, architectural decisions that are easy to get wrong, and facts worth remembering.

## Terminology

- **FF**: Firefox, the project's target browser.
- **HID**: Human Interface Device (USB/Bluetooth input devices).
- **WS / WT / NM**: WebSocket / WebTransport / Native Messaging, the three data-plane transports of the `dataPlane` setting.
- **SAB**: SharedArrayBuffer (removed from the data plane in 2026-07, see below).
- **TLV**: Type-Length-Value, the binary wire format for packed NM messages and collections.
- **VID / PID**: Vendor ID / Product ID (USB device identifiers).
- **COOP / COEP**: Cross-Origin-Opener-Policy / Cross-Origin-Embedder-Policy (cross-origin isolation headers).
- **IPC**: Inter-Process Communication.
- **GC**: Garbage Collection.

## Zero-copy on hot paths, but know which paths are hot

Profiler analysis (paint-by-paint delta) found WS on the content-script main thread ("bridge-direct") loses late-phase throughput to NM. WS receive/parse shares CPU with page rendering (CanvasKit/WASM); NM's subprocess is CPU-isolated. Moving WS onto a dedicated Worker fixes it. This is a real tradeoff, confirmed by data, not a bug. It is different from the old (mistaken) "worker needed to avoid blocking main thread for Atomics" belief. That one was never real; this CPU-contention one is profiler-confirmed.

## Respect hard architectural ceilings, but verify they're real first

Don't accept "this is the ceiling" from an agent (including yourself) without verifying. This project has repeatedly mistaken a bug for an architectural ceiling:

- Worker + SAB was reported as "already at the performance ceiling". Worker+SAB was never actually engaging; everything was silently falling back to NM. Full log + source review found the real bug.
- "SAB push must run on a Worker to avoid blocking main thread via `Atomics.wait`" was carried as fact from a code comment, never re-verified after the drain path moved to `Atomics.waitAsync` (non-blocking). That mechanism was never in the flow. The general concern was real: WS receive/parse on the main thread contends with rendering (profiler-confirmed, 510 vs 681 msg/s late-phase). The instinct was right; the justification was wrong. Two different claims; don't conflate them.
- "SAB is zero-copy, so it must be the fastest" was false by half. SAB write is zero-copy (network to SAB), but drain still needs one copy out, because `HIDInputReportEvent` needs exclusive ownership and the SAB slot gets overwritten by the next report. The no-SAB path (`postMessage` + Transferable) is zero-copy end to end: transfer grants exclusive ownership in one step.
- "Transfer the whole WS frame buffer to the page instead of copying the payload" (the 1000Hz fast path) broke Chromium WebHID semantics. `HIDInputReportEvent.data` is a `DataView`; pages do `new Uint8Array(event.data.buffer)`. A sub-view with non-zero `byteOffset` over the WS frame exposes framing bytes, and offset-based access throws `RangeError`. Contract: `event.data.buffer.byteLength` must equal `event.data.byteLength`, i.e. `byteOffset === 0`. The fast path saved ~30-50µs per report but was reverted. Lesson: "zero-copy" is not one property; count copies and shape changes for the whole journey to the consumer, and the consumer's contract on `.buffer` is part of that journey.
- Before concluding a hard limit, check actual logs/behavior, not just a plausible-sounding explanation.

## SAB removed entirely (2026-07)

After the ring-buffer alloc-size bug was fixed (see below), SAB was benchmarked against a simpler no-SAB path and lost, while carrying ongoing costs (COOP/COEP requirement, Atomics/ring-buffer complexity). Decision: remove SAB entirely. It was not wrong from the start: NM's real burst/latency problems justified trying it, and pursuing SAB forced the investigation that found the alloc bug and the CPU contention. It was a necessary rung, not wasted effort. The removal is evidence-based.

**Final WS data-plane architecture:**
`daemon <-WS-> Worker (no SAB) <-MessageChannel port, transferred once at setup-> page (main thread)`

- The Worker owns the WS connection, allocates the buffer, and posts each report directly to the page via a `MessagePort` transferred once during setup. One hop per report, zero copies, CPU-isolated from rendering.
- The bridge only does three things: (1) spawns the worker, (2) creates and relays the MessagePort to the page once at setup, (3) despawns/respawns workers on settings changes. It sits on no per-message hot path.
- Worker types are independent, with no shared state. **Data Worker**: per-device, spawned on `open()`, killed on device close.
- A 2-hop relay (worker → bridge → page, both via Transferable `postMessage`) is the fallback if direct `MessagePort` transfer fails; direct port is primary.
- The data plane can switch mid-session (WS ↔ NM) via one control-plane command that re-routes that device's reports. No ack/handshake. A report duplicated or dropped during the switch instant is accepted as a user-caused edge case.

## Rate-gated WS batching (2026-08)

**Problem**: under a render-saturated main thread (sayodevice-style CanvasKit/WASM load), WS loses ~1.6-4.3% of input reports in some runs at 8000Hz; NM drops 0. Mechanism (mozilla-central, source-verified 2026-08): WS-to-worker delivery is gated by the content process's main thread. The socket process parses WS frames and sends them via PWebSocket IPC; the content side receives them on the main thread (`RecvOnBinaryMessageAvailable`) and forwards through an unbounded `ChannelEventQueue`. There is no drop mechanism; under saturation the messages queue and arrive late, counted as lost after the drain window. A 5s drain-stability probe still showed ~0.2% "loss" (delivery can stall beyond 5s, a visible freeze). The worker is CPU-isolated for its own work, but the WS-to-worker forwarding still crosses the saturated main thread. nm is immune: its receive runs in the background process.

**Drop curve (measured)**: apparent loss scales with WS frame rate, falling faster than linearly with frame size: ~1-4% at ~1000-8000 frames/s, ~0.5-0.8% at 250/s, 0 at 125/s. Confined to report rates >= ~3kHz; at 2000Hz the fast path shows zero drops. This is the signature of queuing delay (fewer frames → shallower queue → delivery completes within the window), not a per-frame drop probability.

**Fix**: `run_sender` in `crates/webhid-daemon/src/batching.rs` tracks a sliding report-rate estimate (reports flushed per 4ms window). At 12 reports/4ms (~3kHz), frames accumulate to ~8ms instead of flushing per ~1ms; sparse traffic keeps the 25µs coalesce path, so normal-rate latency is unchanged (p50 0.86-0.92ms before and after). Render-load loss dropped from 4.32% worst-run to 0.000-0.583% (~10-20x better; residual is delivery stalling beyond the drain window). WT shares `run_sender`, so WebTransport gets the same protection (render-load loss 0.000 verified).

**Tradeoff**: streams >= ~3kHz pay up to 8ms delivery latency (reports arrive in 8ms chunks, all present and in order; invisible for a high-rate analog graph). Knobs: `WEBHID_WS_HIGH_RATE_MS` (8), `WEBHID_WS_RATE_WINDOW_MS` (4), `WEBHID_WS_HIGH_RATE_COUNT` (12). A fixed `WEBHID_WS_BATCH_MS` interval path also exists. Do not remove the rate gate because the fast path looks fine at low rates: the drop only manifests under sustained high-rate streams plus a busy main thread, which idle benchmarks never exercise.

**Test coverage**: the plain loss benchmark cannot see this bug (idle pages never drop). Reproducing it needs the 8000Hz loss workload on a render-saturated page (fixed per-frame compute + canvas load).

## When a tradeoff has no universally correct answer, expose it as a setting

The data plane is a single `dataPlane` setting (`ws` / `wt` / `nm`). The control plane (handshake, open/close, setDataPlane) always goes over the NM port in the background. That was not always the layout: a control-plane toggle shipped first (`6cec6bd`), then the ws control channel was removed in `c964326` (2026-07-22, breaking, 441 lines deleted). Reason: NM control verifies the peer at the OS level (SO_PEERCRED + webhid group check on the abstract socket) on top of the session token; ws control was token-only (subprotocol, 4401/4402 errors), so a token holder could drive control without the OS identity check. Control stays on the stronger channel.

The default flipped from `ws` to `wt` in 2026-08, driven by profiler data. WS delivery crosses the content main thread (PWebSocket IPC → `RecvOnBinaryMessageAvailable` → `ChannelEventQueue`), costing ~18pp of content main-thread CPU and 3.8x the main-thread IPC of WT under the render-heavy benchmark. WT delivers through a DataPipe shared-memory read on the worker with zero WebSocket IPC. Default is `wt` when `WebTransport` exists, `ws` on older Firefox. WS is the fallback when the WT port is not offered or the page CSP forces NM.

## Project-specific facts worth remembering

- The benchmark's `open` metric (38-58ms) is NOT a daemon regression. It is `open()` itself (~15ms: worker spawn + NM control round trip + collections) plus a one-time ~25ms first-WS-message penalty inside Firefox's WS IPC (measured 2026-08; subsequent sends are ~0.7ms round trip). Per-connection, send-direction, invisible for input-heavy use. The docs' older 20-23ms numbers measured a phase without the penalty.
- The daemon has two deployment modes: (1) persistent root daemon + thin NM-host forwarder over Unix socket, for setups without udev rules; (2) daemon-as-NM-host, spawned by Firefox, running as the user, requiring udev rules. They serve different permission setups; both must keep working.
- The e2e suite is a multi-device harness. Each generated descriptor is its own mock device at VID 0x16c0, with per-type PIDs from `DEVICES` in `tests/helpers/e2e-devices.ts` (vendor=0x0001, gamepad=0x0002, mouse=0x0003, keyboard=0x0004). Devices spawn lazily and are reused across the serial chain. Vendor (report ID 1, 64-byte input/output) drives the primary chain and feature-report coverage (the daemon issues raw SET/GET_REPORT ioctls regardless of declaration). Gamepad (no report ID, 5-byte input) drives the WS-data-plane-with-URL-fragment and fresh-pairing gates. Two traps are now encoded in the fixtures:
  - **Daemon blocklist**, verified 1:1 against Chromium/WICG on 2026-08-03, two layers. (1) Device-level (`hid.rs`): FIDO usage page 0xF1D0 + per-product security-key list, matching Chromium's `kStaticEntries`; matched devices are hidden from enumeration. (2) Report-level (`blocklist.rs`/`report_blocking.rs`): matches WICG `blocklist.txt` entry-for-entry (FIDO, GD Mouse/Keyboard/Keypad/SystemControl, Jabra, OnlyKey), always-on like Chromium. Mirrors Chromium exactly: any-match per (report_id, type) over a report→collection map where each report carries every ancestor collection's usage (so a Mouse report in a Physical child IS blocked); plus hardcoded always-protected usages (page 0x07; GD Pointer/Mouse/Keyboard/Keypad; GD SystemControl 0x80-0x8f, 0xa0-0xb6); plus two fallbacks (undocumented report IDs block when the device has an always-protected top-level; unparseable/empty descriptors block when the hidapi interface usage is protected). Input dropped at the reader; output/feature rejected. Sends are pre-checked like Chromium's `HidConnection::Write`, with one deliberate exception: a report type not declared in the descriptor stays allowed (raw ioctls; e2e feature coverage relies on this). Blocked reports are pruned from the page-visible `collections` tree (`prune_device_info` at enumerate + hotplug); all-empty devices are hidden. SayoDevice config uses distinct report IDs, so only its keyboard report 1 is blocked. Historical trap: a top-level usage match used to hide the whole device (pre-2026-08); gone, but with `report-blocking` on, keep fixtures off Mouse/Keyboard/Keypad usages if they must receive reports.
  - **Usages must cover a non-constant main item's report count**: `hidreport` rejects "Missing Usages for main item" when reportCount exceeds the declared usages and the item is Data/Variable. Const items sidestep the check.
  - **Concurrent-run WS drop**: running the two e2e projects concurrently (without `--workers=1`) occasionally drops a vendor input report (`oninputreport` never fires) due to WS data-plane CPU contention between the two stacks. Each project passes 19/19 alone; serializing (`--workers=1`, 38 tests) passes 38/38 deterministically. For the "both projects pass" verification, use `--workers=1`.
- Firefox 150+ gates page-context WebTransport to loopback (Local Network Access, `network.lna.blocking` default true): a PUBLIC origin hitting a local address gets a one-time "Allow" prompt. Loopback-origin pages and worker-context WT are exempt. The old "the harness can't do in-page WT" claim was wrong twice over (verified 2026-08-03): the stall was Playwright `context.route('**/*')` interception, not LNA. Juggler routes via the service-worker intercept API, which redirects the WebTransport channel (`SetupReplacementChannel`) and cancels it with `NS_ERROR_NOT_AVAILABLE`, so `wt.ready` never settles and the bridge falls back to NM after 10s. Fix: no catch-all route in `tests/helpers/e2e.ts`. Do not reintroduce one: page-context WebTransport cannot survive Juggler interception.
- macOS: Input Monitoring (TCC) permission required for `IOHIDManager`; must be granted manually, no programmatic prompt. Windows: no special permission (`HidD_*`). Linux: mostly `udev`/`eudev`, Alpine defaults to `mdev`.
- Consent model (2026-08-06): a page cannot grant itself a device or see the full inventory. `pairDevice`/`recordGrantGroup`/`getGrantGroups`/`getAllPairedDevices`/`revokeDevice`/`getDeviceCache`/`getDeviceInfo`/`showPicker`/`pickerResult` are blocked from page ports in the bridge (`PAGE_BLOCKED_ACTIONS`, 403 reply). Page `enumerate` is rewritten to `enumeratePaired`, and the background filters the response to the requesting origin's paired hashes (the chooser and extension pages call `enumerate` directly and see everything). Pairing runs in the bridge after the user selects in the chooser (`grantSelectedDevices`). `pickerResult` is rejected unless `sender.url` is the extension's picker page. Devices granted together form a grant group (`recordGrantGroup`, IndexedDB `grantGroups`); revoking any member cascades to the group (`revokeDevice`), and each affected page device settles pending sends with `AbortError` via the `revoked` event. The polyfill's `forget()` un-pairs the single device it is called on.
- Permissions Policy trust basis (2026-08-09): the `getPolicy` cross-origin allow decision no longer trusts any frame URL the MAIN world self-reports. The MAIN-world `getCallerFrameUrl()` (stack-trace parsing via `new Error().stack`, with a `location.href` fallback) was removed: the MAIN world shares `window` with page script, so both `window.Error` and `location` are page-overridable, letting a cross-origin iframe forge a sibling's `allow="hid"` src. The bridge now derives `hasAllowAttr` from the requesting port's source `Window` (engine-set `event.source`) matched against `iframe[allow*="hid"]` in the top document, cross-checked against the port's `event.origin` (also engine-set); the `url` it forwards to the background is that same port origin, never a document URL from the MAIN world. `request.hasAllowAttr` and the `allowedCrossOrigin` map in `policyForRequest` are unchanged; only their inputs became unforgeable. Regression coverage: the forge test in `tests/browser/permissions-policy.spec.ts`.
- Worker polyfill gating (2026-08-09): page-created workers only receive the init message (`null` + MessagePort, which becomes the worker polyfill's bridge port) when worker-polyfill injection is active for the WORKER SCRIPT's origin, not the embedding page's. The decision is made SYNCHRONOUSLY at spawn time from a cached state: the bridge computes `{ global, origins }` (`loadGlobalSettings().workerPolyfillEnabled` plus every site key whose `workerPolyfillEnabled` is set) on a `workerPolyfillState` request at document_start, pushes recomputed state on any storage change, and the MAIN world keeps the cache in `workerPolyfillState`; `PatchedWorker` resolves the worker URL's origin (skipping `blob:`/`data:` workers, which cannot be injected) and reads the cache, so no async round trip gates the spawn. A setting change whose push arrives after a worker spawn leaves that worker on the old value; that lag is accepted. Previously the init port was sent to every page worker unconditionally, so a plain worker (no injection) received a spurious `null` message as its first message and its own `onmessage` protocol broke. The worker-side polyfill now calls `stopImmediatePropagation` on the init message so it never reaches the page worker's own handlers; the polyfill's init listener is registered first because the bundle is prefixed into the worker script. One consequence: a page-created shadow worker (`new Worker(location.href)`, whose script `handleShadowUrl` replaces with the data bundle) no longer receives the init when the setting is off. The data bundle's `null`+port `'ready'` reply branch was removed: it was only ever observed by the dest-gated test page's completion signal, and production data workers spawn via `NativeWorker` in `handleSpawnWorkerRequest`, are driven by `setPorts`, and signal readiness over the control port via the transport `onReady` callback. `tests/pages/dest-gated.html` uses a `settled` timeout fallback as its completion signal, so the shadow-redirect tests no longer depend on the extension's init behavior. The state push reaches window ports only (`replyToPage` broadcast), so nested-worker polyfill contexts refresh their cache only at their own startup. Cross-origin worker scripts cannot be exercised in the browser harness: the service-worker network bridge re-serves responses without CORS headers, so a cross-origin worker fetch fails (same class of limitation as the WebTransport interception note). Regression coverage: the gating tests in `tests/browser/worker.spec.ts`.
- The polyfill runs in the page's JS realm (MAIN world), so it pre-claims pristine `MessagePort`/`MessageChannel`/`Worker.prototype.postMessage`/`window.postMessage` natives at document_start. Page prototype patches cannot capture the bridge port anymore. Two gotchas, each costing a debug cycle: (1) `addEventListener` does not implicitly start a `MessagePort`; call `start()` explicitly, or responses never dispatch and every sendRequest limps on its 30s timeout. (2) `window.postMessage` targets the `this` window; never bind it when an iframe polyfill posts its port to `window.top` (a bound call silently posts to the wrong window; only the cross-origin iframe browser tests catch this). Regression coverage: `tests/e2e/picker-bypass.spec.ts`.
- SAB ring buffer: 8192 slots sized by an _estimated_ max report size produced a 16MB init allocation that erased SAB's round-trip advantage. Fixed by computing exact per-report size at parse time and defaulting to 64 slots (later removed with SAB). Drain never needed >1 occupied slot in practice, even at 8000Hz.
- NM messages: hot-path input reports use packed binary TLVs (`PKG_SEND_REPORT` 0x02, `PKG_SEND_FEATURE_REPORT` 0x04, `PKG_INPUT_REPORT` 0x01) as base64 in one JSON field `{"d":"<b64>"}`; collections use a TLV module (`crates/webhid/src/collections_tlv.rs`, `[tag:u8][len:varint][value]`, unknown-tag skip; JS decoder `addon/js/utils/descriptor-tlv.js` at cache time). Compression was rejected (CPU/alloc cost outweighs savings at this size). NM has a real 1MB message ceiling (app→browser); worth a daemon-side sanity check if a message ever approaches it.
- CSP relaxation via webRequest depends on manifest version (verified 2026-08): MV2 may fully replace or strip a page's CSP ([bug 1635781](https://bugzilla.mozilla.org/show_bug.cgi?id=1635781), FF79+); MV3 is "strengthen only", the original policy is always enforced cumulatively ([bug 1785821](https://bugzilla.mozilla.org/show_bug.cgi?id=1785821), FF106+; header merging from [bug 1462989](https://bugzilla.mozilla.org/show_bug.cgi?id=1462989)). No MV3 full-override permission exists ([bug 1787155](https://bugzilla.mozilla.org/show_bug.cgi?id=1787155), open). The default `manifest.json` is MV3, so blob-URL workers + CSP rewriting cannot work there (only under `manifest.v2.json`). Content scripts cannot spawn workers from `moz-extension://` URLs either (fetch succeeds, worker load fails silently on a cross-origin check). Consequence: when a page's CSP blocks the shadow worker, the only MV3 fallback is NM. The background does CSP pre-flight (`csp:tabId:frameId`, `getCspInfo`) so the bridge skips the doomed spawn. Do not propose blob-URL workers + CSP rewriting for the MV3 build again.
- Polyfill-polyfill MessagePort race (2026-07): same-origin iframes each run a polyfill, each sending a `MessageChannel` port to the bridge; both start request IDs at 0, and the bridge's `requestPortMap` is keyed by numeric ID, so concurrent requests collide (wrong-frame delivery + dropped response). Fix: prefix IDs with a per-polyfill `crypto.randomUUID()` nonce (`frameNonce + ':' + ++nextReqId`).
- Cold-start methodology: a local clone of sayodevice.com removed network-load variance (which pushed GC into benchmark windows). The last variance source, human click timing, is gone too: the benchmark is Playwright-driven, and Chromium grants via policy.
- Automated image-pipeline benchmark (2026-08, `tests/benchmark/`, see [docs/BENCHMARK.md](docs/BENCHMARK.md)) confirmed a burst-drop the e2e suite never sees (single reports): a burst of ~330 consecutive reports drops on the page side (ws 30-36, nm 7-37 mid-session), and the FIRST burst after cold start or a data-plane switch is the lossiest. The benchmark invalidates dropped-report runs and retries, plus runs an unmeasured warm-up burst per cold-start spec to absorb first-burst losses. Do not extrapolate to normal use: the e2e suite at its normal rate is drop-free.
- Hung-ack root cause (2026-08): the data worker kept in-flight send promises in `pending` and never settled them when the WS dropped, leaving the page's sendReport pending forever. Fix: `onClosed` rejects and clears all pending entries; the page gets a fast `'ws closed'` rejection and retries. Benchmark-side pitfalls: prime with an awaited 128-report burst, time-boxed per send (a fire-and-forget variant inflated the ws total by ~2s; a single global gate falsely failed slow primes).
- Exploratory branches, curiosity-driven (don't assume benchmark-justified):
  - **WebTransport/QUIC data-plane**: `dataPlane: "wt"` is a working third transport. Daemon starts a WT server at boot (self-signed ECDSA P-256, SAN 127.0.0.1, ≤14-day validity, pinned via `serverCertificateHashes`); auth reuses the WS scheme via the URL path; one persistent bidirectional stream per session with a `[len_u32 LE]` frame prefix; cert renewal rotates to a fresh port with drain. Covered by `tests/e2e/wt.spec.ts` + `tests/benchmark/benchmark-wt.spec.ts`. Benchmark (2026-08-02): p50 0.85ms vs ws 0.78ms and nm 1.77ms, so TLS/QUIC costs ~+0.07ms per report on loopback and WT is effectively a free security option; ws remains the fastest Firefox path. Gotchas: `context.route` stalls page-main WT (Juggler cannot carry a WebTransport session); the seccomp allow-list needed `SYS_fcntl` + `SYS_recvmmsg` (quinn-udp uses both; they would have killed the hardened daemon).
  - **Chromium native-WebHID benchmark** (`chromium-benchmark`, fully automated, headless): WebHID cannot be granted via CDP, so the mock is pre-granted with the `WebHidAllowDevicesForUrls` policy and the benchmark's `getDevices()`-based `open()` skips the chooser. Gotchas: (a) policy matches origins including the port, so the benchmark serves on fixed port 8123 and the policy must contain exactly `http://localhost:8123`; (b) default `headless: true` runs `chrome-headless-shell` with no udev/HID layer; `channel: 'chromium'` forces full Chrome for Testing, where enumeration works; (c) `--no-sandbox` breaks udev enumeration, never pass it. Findings: `vendor.bin`'s report ID 1 used to sit _between_ two top-level collections, which Chromium's HID parser does not carry across a boundary (native `sendReport(1, ...)` failed); the ID now lives inside the vendor collection. Per the spec, `HIDInputReportEvent.data` excludes the report ID byte, so Chromium native and the polyfill deliver identical framing. Chromium p50 ~0.3-0.4ms; do not read "polyfill faster than native Chromium" from any Firefox number. Chromium's `performance.now()` is clamped to 100µs (crbug 438389473, open); the benchmark page uses COOP/COEP headers for 5µs precision.
  - **Chromium testbed**: overriding `navigator.hid` on Chromium (works) to compare the polyfill against native WebHID on the same engine, isolating "polyfill tax" from engine differences. Not yet benchmarked; do not claim the polyfill beats native Chromium until real numbers exist.

## Not every change needs a benchmark-driven justification

Some changes were made because they were interesting to try, not because a benchmark demanded them (binary-packed collections, WebTransport exploration). That is legitimate on its own. Don't retroactively invent a performance rationale for a curiosity-driven change; note it as such.

## Writing style: no em-dashes

Don't use em-dashes ("—") anywhere in this document or in any writing produced for this project. Rewrite with smoother sentence flow (subordinate clauses, "since"/"so"/"which", or splitting into two sentences), or fall back to a comma, colon, semicolon, or parentheses when a harder break is actually needed. Em-dash is a style tic to actively avoid, not just deprioritize.
