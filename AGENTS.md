# Agent Guidelines for FF-WebHID

Before you act, read `CONTRIBUTING.md` for the project's design principles. They apply to you too.

This file contains agent-specific context: historical gotchas, architectural decisions that are easy to get wrong, and facts worth remembering that won't fit in CONTRIBUTING.md.

## Terminology

- **FF**: Firefox, the project's target browser.
- **HID**: Human Interface Device (USB/Bluetooth input devices).
- **WS / WT / NM**: WebSocket / WebTransport / Native Messaging, the three data-plane transports of the `dataPlane` setting.
- **SAB**: SharedArrayBuffer (removed from the data plane in 2026-07, see below).
- **TLV**: Type-Length-Value, the binary wire format used for packed NM messages and collections.
- **VID / PID**: Vendor ID / Product ID (USB device identifiers).
- **COOP / COEP**: Cross-Origin-Opener-Policy / Cross-Origin-Embedder-Policy (cross-origin isolation headers).
- **IPC**: Inter-Process Communication.
- **GC**: Garbage Collection.

## 3. Zero-copy by default on hot paths, but know which paths are hot (case study)

Profiler analysis (paint-by-paint delta) found WS running on the content-script main thread ("bridge-direct") loses late-phase throughput to NM, because WS receive/parse has to share CPU with page rendering (CanvasKit/WASM), while NM's subprocess is CPU-isolated. This is a genuine architectural tradeoff, confirmed by data, not a bug. Moving WS onto a dedicated Worker fixes it. Note this is a _different_ reason than the old (mistaken) "worker needed to avoid blocking main thread for Atomics" belief below; that one was never real, while this CPU-contention one is profiler-confirmed.

## 4. Respect hard architectural ceilings, but verify they're real first (historical record)

Don't accept "this is the ceiling" from an agent (including yourself) without verifying. This project has repeatedly mistaken a bug for an architectural ceiling:

- Worker + SharedArrayBuffer was reported as "already at the performance ceiling" by an earlier agent, when it turned out Worker+SAB was never actually engaging, and everything was silently falling back to Native Messaging. Full log + source review (not just a described architecture) found the real bug.
- "SAB push must run on a Worker to avoid blocking main thread via `Atomics.wait`" was carried as fact from a code comment, never re-verified after the drain path moved to `Atomics.waitAsync` (non-blocking). That specific mechanism (blocking wait) was never actually in the flow, so that particular rationale didn't apply. But the _general_ concern, that running WS receive/parse on main thread contends for CPU with rendering, turned out to be real, and was confirmed later by profiler data (see the CPU-contention case study in Section 3): bridge-direct doesn't crash or visibly jank, but it does lose real throughput (510 vs 681 msg/s late-phase) under a render-heavy scenario. So the instinct to keep WS off the main thread was right, even though the specific justification given for it (blocking Atomics) was wrong. Two different claims; don't conflate them when reading this history.
- "SAB is zero-copy, so it must be the fastest data-plane option" turned out false by half. SAB write is zero-copy (network to SAB), but drain still requires one copy out to a fresh buffer, because `HIDInputReportEvent` needs exclusive ownership and the SAB slot gets overwritten by the next report. The no-SAB path (bridge to page via `postMessage` + Transferable) has zero copies end to end, since transfer grants exclusive ownership in one step.
- "Transfer the whole WS frame buffer to the page instead of copying the payload into a fresh ArrayBuffer" (the 1000Hz single-report fast path) sounded like a clean zero-copy win, but it broke Chromium WebHID semantics. `HIDInputReportEvent.data` is a `DataView`, and pages reasonably do `new Uint8Array(event.data.buffer)`. If the DataView is a sub-view with non-zero `byteOffset` over a larger buffer (the WS frame including the length prefix + report ID), `event.data.buffer` exposes the framing bytes, not just the payload, and any offset-based access into it throws `RangeError`. The fast path saved ~30-50µs per report (one alloc + one copy) but had to be reverted: `event.data.buffer.byteLength` must equal `event.data.byteLength`, i.e., `byteOffset === 0`. The lesson is the same as the SAB one above: "zero-copy" is not a single property; you have to count the copies and shape changes for the whole journey to the consumer, and the consumer's contract on `.buffer` is part of that journey.
- Before concluding something is a hard limit, check actual logs/behavior, not just a plausible-sounding architectural explanation.

## SAB removed entirely (2026-07)

After the SAB ring-buffer alloc-size bug was fixed (see below), SAB was benchmarked against a simpler no-SAB path and lost, while also carrying real ongoing costs (cross-origin isolation requirement, COOP/COEP injection risk, Atomics/ring-buffer complexity). Decision: remove SAB entirely rather than keep it as an "opt-in performance mode." This was not SAB being wrong from the start. NM's real burst/latency problems were the original justification for trying SAB, and pursuing SAB is what forced the investigation that uncovered the alloc bug and the CPU-contention finding above. SAB was a necessary rung on the ladder, not wasted effort; the decision to remove it is evidence-based (post-benchmark), not assumed upfront.

**Final WS data-plane architecture:**
`daemon <-WS-> Worker (no SAB) <-MessageChannel port, transferred once at setup-> page (main thread)`

- Worker owns the WS connection, allocates the buffer, and posts each report directly to the page through a `MessagePort` transferred once during setup: one hop per report, zero copies, and CPU-isolated from rendering.
- Bridge (content script) only does three things: (1) spawns the worker, (2) creates and relays the MessagePort to page once at setup, (3) despawns/respawns workers when the user changes settings. It does not sit on any per-message hot path anymore, for either control or data plane.
- Two independent worker types, with no shared state or dependency between them:
  - **Data Worker**: per-device, spawned on `open()`, killed on device close.
- A 2-hop relay (worker to bridge to page, both via Transferable `postMessage`) is the fallback path if direct `MessagePort` transfer ever fails; direct port is primary.
- Data-plane transport can be switched mid-session (WS <-> NM) via a single control-plane command telling the daemon to re-route that device's reports, with no ack/handshake. A report being duplicated or dropped during the switch instant is accepted as a user-caused edge case, not engineered around.

## Rate-gated WS batching (2026-08)

**Problem**: under a render-saturated page main thread (sayodevice-style CanvasKit/WASM load), the WS data plane loses ~1.6-4.3% of input reports in some runs at 8000Hz polling (the user's jagged analog graph). NM drops 0 under the identical load. Source-verified mechanism (mozilla-central, 2026-08): the WS-to-worker message delivery is gated by the content process's main thread. The socket process parses the WS frames and sends them to the content process via PWebSocket IPC; the content side receives them on the main thread (WebSocketChannelChild::RecvOnBinaryMessageAvailable) and forwards through an unbounded ChannelEventQueue to the worker. There is no drop mechanism in this path (queues are unbounded; the parent drops only when the IPC actor is closing). Under main-thread render saturation the messages queue and are delivered late; the benchmark's drain window ends while the queue is still backed up, counting the queued reports as lost. A 5s drain-stability probe still showed ~0.2% "loss" under the synthetic near-continuous load, i.e. delivery can stall beyond 5s (a visible freeze), so for real-time use the delayed reports are effectively lost. The worker is CPU-isolated for its own parse/port work, but the WS-to-worker forwarding still crosses the saturated main thread. nm is immune because its receive runs in the background process.

**Drop curve (measured)**: the apparent loss scales with the WS frame rate, falling faster than linearly with frame size: ~1-4% at ~1000-8000 frames/s, ~0.5-0.8% at 250/s, 0 at 125/s. The phenomenon is confined to report rates >= ~3kHz; at 2000Hz the fast path shows zero drops. This is the measured signature of the queuing-delay mechanism (fewer frames -> shallower main-thread queue -> delivery completes within the measurement window), not a per-frame drop probability in Firefox code.

**Fix**: `run_sender` in `crates/webhid-daemon/src/batching.rs` tracks a sliding report-rate estimate (reports flushed per 4ms window). When the sustained rate reaches 12 reports/4ms (~3kHz), frames accumulate to ~8ms instead of flushing per ~1ms; sparse traffic keeps the 25us coalesce path, so round-trip latency for normal rates is unchanged (measured: latency p50 0.86-0.92ms before and after). Render-load loss dropped from a 4.32% worst-run baseline to a 0.000-0.583% spread across five official runs in the default harness position (mean ~0.12-0.5% depending on machine warmth, i.e. ~10-20x better; the residual is delivery stalling beyond the drain window under near-continuous saturation). e2e 128 passed, 101 daemon unit tests. WT shares `run_sender`, so the WebTransport plane gets the same protection (render-load loss 0.000 verified).

**Tradeoff**: streams >= ~3kHz pay up to 8ms of delivery latency (reports arrive in 8ms chunks, all present and in order). For a high-rate analog graph this is invisible (125Hz chunk cadence, no holes); the env knobs `WEBHID_WS_HIGH_RATE_MS` (8), `WEBHID_WS_RATE_WINDOW_MS` (4), `WEBHID_WS_HIGH_RATE_COUNT` (12) tune the window and the gate. A fixed `WEBHID_WS_BATCH_MS` interval path also exists for users who want constant time-based batching. Do not "optimize away" the rate gate because the fast path looks fine at low rates: the drop only manifests under sustained high-rate streams plus a busy main thread, which the idle benchmarks never exercise.

**Test coverage**: the plain loss benchmark cannot see this bug (idle pages never drop); reproducing it requires the 8000Hz loss workload on a render-saturated page (a fixed per-frame compute + canvas load).

## 9. When a tradeoff has no universally correct answer, expose it as a setting (implementation detail)

The data-plane transport is a single `dataPlane` setting with three values (`ws` / `wt` / `nm`); the control plane (handshake, open/close, setDataPlane) always goes over the NM port in the background. That was not always the layout: a control-plane toggle shipped first (`6cec6bd`, ws control and nm control, later with an Advanced section exposing control and data as independent toggles, a clean 4 = WS/NM x WS/NM, down from 6 historical combos that included SAB variants). The ws control channel was then removed in `c964326` (2026-07-22, breaking, 441 lines deleted) because it was missing one defense-in-depth layer: NM control verifies the peer at the OS level (SO_PEERCRED + webhid group check on the abstract socket) on top of the session token, while ws control was token-only (Sec-WebSocket-Protocol subprotocol, 4401/4402 errors), so a token holder could drive control without the OS identity check. Removal kept control on the stronger channel and left `dataPlane` as the single ws/wt/nm data setting.

The default flipped from `ws` to `wt` in 2026-08, driven by profiler data: WS delivery crosses the content main thread (PWebSocket IPC into RecvOnBinaryMessageAvailable, then ChannelEventQueue into the worker), which costs ~18pp of content main-thread CPU and 3.8x the main-thread IPC of WT under the render-heavy image-pipeline benchmark; WT delivers through a DataPipe shared-memory read on the worker with zero WebSocket IPC. The default is `wt` when `WebTransport` exists, `ws` on older Firefox. WS remains the fallback whenever the WT server port is not offered by the daemon (the bridge falls back to ws) or the page CSP forces NM.

## Project-specific facts worth remembering

- The benchmark's `open` metric (38-58ms) is NOT a daemon regression: it is `open()` itself (~15ms: worker spawn + NM control round trip + collections) plus a one-time ~25ms first-WS-message penalty inside Firefox's WS IPC (measured 2026-08: the daemon's first write is 86us and the worker's `ws.send` call is 0.02-0.16ms, so the 25ms is in the browser's socket-to-content path; subsequent sends are ~0.7ms round trip). It is per-connection, send-direction, and invisible for input-heavy use (the echo/report receive path stays fast). The docs' older 20-23ms open numbers measured a phase without the first-message penalty.

- The daemon has two deployment modes: (1) persistent root daemon + thin NM-host forwarder over Unix socket, for setups without udev rules configured; (2) daemon-as-NM-host, spawned directly by Firefox, running as the user, requiring udev rules to be set up. These aren't redundant; they serve different permission setups and should both keep working.
- The e2e suite is a multi-device harness: each generated descriptor is its own mock device at VID 0x16c0 with a per-type PID from `DEVICES` in `tests/helpers/e2e-devices.ts` (vendor=0x0001, gamepad=0x0002, mouse=0x0003, keyboard=0x0004). Devices spawn lazily and are reused across the serial chain. The vendor fixture drives the primary chain (report ID 1, 64-byte input/output); gamepad (no report ID, 5-byte input) drives the WS-data-plane-with-URL-fragment and fresh-pairing gates. Feature-report coverage (send/receive at report ID 0x02) runs on the vendor device because the daemon issues raw SET/GET_REPORT ioctls regardless of whether the descriptor declares a feature item. Two non-obvious traps cost real debugging time and are now encoded in the fixtures/generator so they don't recur:
  - **Daemon blocklist**, verified 1:1 against Chromium/WICG on 2026-08-03: two layers. (1) Device-level (`hid.rs`): FIDO usage page 0xF1D0 + per-product security-key list, matches Chromium's `kStaticEntries`; matched devices are hidden from enumeration. (2) Report-level (`blocklist.rs`/`report_blocking.rs`): rules match WICG `blocklist.txt` entry-for-entry (FIDO, Generic Desktop Mouse/Keyboard/Keypad/SystemControl, Jabra, OnlyKey), enforced unconditionally like Chromium (no gate, matching Chromium's always-on blocklist). Mirrors Chromium exactly: any-match per (report_id, type) over a report→collection map where each report carries every ancestor collection's usage (hid_collection.cc propagation, so a Mouse report in a Physical child IS blocked); plus the hardcoded always-protected usages (usage page 0x07; GD Pointer/Mouse/Keyboard/Keypad for input/output; GD SystemControl 0x80-0x8f and 0xa0-0xb6); plus two fallbacks: undocumented report IDs block when the device has an always-protected top-level of that type, and unparseable/empty descriptors (e.g. a boot-keyboard interface) block when the hidapi interface usage is protected. Input reports dropped at the reader, output/feature writes rejected. Sends are also pre-checked like Chromium's `HidConnection::Write` (report ID must match the device's numbered-report mode, payload within the declared max size); the one deliberate exception is a report type not declared in the descriptor at all, which stays allowed because the daemon issues raw SET/GET_REPORT ioctls regardless of declaration (the e2e feature-report coverage relies on this). Blocked reports are also pruned from the page-visible `collections` tree (`prune_device_info`, applied at enumerate + hotplug connect events), and a device whose collections all become empty is hidden entirely, matching Chromium's `RemoveProtectedReports` + `OnDeviceAdded`. SayoDevice (0x8089:0x0009) config interface uses distinct report IDs, so only its keyboard report 1 is ever blocked and the vendor config reports pass. Historical fixture trap: a top-level usage match used to hide the whole device (pre-2026-08); that is gone, but with `report-blocking` on, keep fixtures off Mouse/Keyboard/Keypad usages if they must receive reports.
  - **Usages must cover a non-constant main item's report count**: `hidreport` rejects "Missing Usages for main item" when reportCount exceeds the number of usages declared and the item is Data/Variable rather than Constant. The old switchpro fixture dodged this with Const items, which sidestep the check.
  - **Concurrent-run WS drop**: running the two e2e projects concurrently (`--project=firefox-e2e --project=firefox-e2e-daemon-nm` without `--workers=1`) occasionally drops a vendor input report: the daemon reader is alive and its WS is connected, the report is pushed, but the page's `oninputreport` never fires (`saw: []`). This is WS data-plane CPU contention between the two heavy Firefox+daemon stacks, consistent with the profiler-confirmed contention in the architecture notes. Each project independently passes 19/19; serializing them (`--workers=1`, 38 tests) passes 38/38 deterministically. For the "both projects pass" verification, run with `--workers=1`.
- Firefox 150+ gates page-context WebTransport to local/loopback addresses (Local Network Access, `network.lna.blocking` default true): a PUBLIC origin connecting to a local address gets a one-time "Allow" local-network permission prompt, then the decision is remembered per origin. Loopback-origin pages are exempt at the transaction layer (Local to Local is not a privacy escalation, `AllowedToConnectToIpAddressSpace`), so the local test pages never prompt. Worker-context WebTransport is exempt too (Juggler routes only page requests; shared/service workers get a promptless permission check). The old claim that "the harness never renders the LNA prompt, so in-page WT is impossible in the harness" was wrong twice over (verified 2026-08-03 with MOZ_LOG + a routed vs unrouted A/B): the harness stall was Playwright `context.route('**/*')` interception, not LNA. Juggler implements routing with the service-worker intercept API, which internally redirects the WebTransport channel (`SetupReplacementChannel`) and cancels the original with NS_ERROR_NOT_AVAILABLE, so `wt.ready` never settles and the bridge falls back to NM after 10s; and the loopback test-page origin would not have prompted anyway. Fix: the harness fixture no longer installs the catch-all route (`tests/helpers/e2e.ts`), and the in-page WT tests now run for real (e2e `wt.spec.ts` "runs in-page when useWorker is off", benchmark `benchmark-wt-inpage.spec.ts`; both passed 58/58 + 7/7 on 2026-08-03). Do not reintroduce a catch-all `context.route` in the harness: page-context WebTransport cannot survive Juggler interception.
- macOS requires Input Monitoring (TCC) permission for `IOHIDManager` access. There's no way to prompt for it programmatically, so the user must grant it manually in System Settings.
- Windows requires no special permission for standard HID access via `HidD_*` APIs.
- Linux permission model varies by distro: most use `udev`/`eudev` (rule-compatible), but Alpine defaults to `mdev` (different config syntax).
- SAB ring buffer defaulted to 8192 slots, sized by an _estimated_ max report size from collection calculations. This produced a 16MB allocation at worker init, adding real native-runtime cost that erased SAB's round-trip advantage over NM in early benchmarks, making them look "equivalent" when they weren't. Fixed by (1) computing exact per-report size from the descriptor at parse time in the daemon instead of estimating, and (2) defaulting slot count to 64, exposed as a user setting (this setting was later removed entirely along with SAB, see above). Debug logs on real devices (SayoDevice) showed drain never lags behind push enough to need more than 1 occupied slot at a time in practice; the multi-slot ring buffer's core justification (absorbing burst when consumer is slower than producer) was not actually observed to trigger, even at 8000Hz polling rate.
- NM messages moved from verbose per-field JSON to a binary packed format for hot-path input reports (sendReport/sendFeatureReport) and cold-path collections. Hot-path messages use packed binary TLVs (`PKG_SEND_REPORT` 0x02, `PKG_SEND_FEATURE_REPORT` 0x04, `PKG_INPUT_REPORT` 0x01) encoded as base64 inside a single JSON field `{"d":"<b64>"}`. Collections use a TLV binary + base64 serde module (`crates/webhid/src/collections_tlv.rs`) with node-based format: `[tag:u8][len:varint][value]`, forward-compat via unknown-tag skip. JS decoder (`addon/js/utils/descriptor-tlv.js`) runs once at cache time in background. Compression was considered and explicitly rejected: for messages this small, compress/decompress CPU and allocation cost outweighs the bandwidth savings. NM has a real 1MB message size ceiling (app to browser direction) enforced by the browser. This isn't a practical concern at current report/collection sizes, but it's worth a daemon-side sanity check/log if a message ever approaches it, guarding against a batching bug silently building an oversized message, similar in spirit to the SAB alloc bug above.
- CSP relaxation via webRequest depends on manifest version (verified 2026-08 on real Firefox): MV2 extensions may fully replace or strip a page's `Content-Security-Policy` ([bug 1635781](https://bugzilla.mozilla.org/show_bug.cgi?id=1635781), Firefox 79+), but MV3 extensions are restricted to "strengthen only", where the original policy is always enforced cumulatively alongside the extension's modification ([bug 1785821](https://bugzilla.mozilla.org/show_bug.cgi?id=1785821), Firefox 106+; header merging behavior introduced in [bug 1462989](https://bugzilla.mozilla.org/show_bug.cgi?id=1462989)). A permission letting MV3 extensions fully override CSP was considered but never shipped ([bug 1787155](https://bugzilla.mozilla.org/show_bug.cgi?id=1787155), meta, still open). This addon's default `manifest.json` is MV3, so blob-URL workers plus CSP rewriting cannot work in that build (it would work under `manifest.v2.json`). Separately verified: content scripts cannot spawn workers from `moz-extension://` URLs (the fetch succeeds with `web_accessible_resources`, but the worker load fails silently on a cross-origin check), so that is not a workaround either. Consequence: when a page's CSP blocks the shadow worker (`worker-src` excluding same-origin, `connect-src` blocking the daemon WS, or `require-trusted-types-for 'script'`), the only fallback in the MV3 build is the NM data plane. The background does CSP pre-flight detection (`csp:tabId:frameId` in `storage.session`, `getCspInfo` message) so the bridge skips the doomed shadow spawn and goes straight to NM. Do not propose blob-URL workers plus CSP rewriting for the MV3 build again.
- Polyfill-polyfill MessagePort race (2026-07): When same-origin iframes each run their own polyfill instance, each polyfill creates a `MessageChannel` and sends `port2` to the bridge via `postMessage`. Both polyfills independently generate request IDs (`++nextReqId` starting from 0). Since the bridge's `requestPortMap` is keyed by numeric ID, concurrent requests from two frames with the same ID (e.g. id=1 for `getSettings`, id=2 for `getPolicy`) overwrite each other, causing one frame's response to be delivered to the wrong frame and the other frame's response to be dropped entirely. Fix: prefix request IDs with a per-polyfill `crypto.randomUUID()` nonce (`frameNonce + ':' + ++nextReqId`), making IDs globally unique across frames.
- Cold-start benchmark methodology matured: a local clone of the test site (sayodevice.com) with URLs patched to load locally removed network-load timing variance, which had been causing GCMajor to intrude into benchmark windows unpredictably (a slow network load could push GC to trigger right as the person clicked, corrupting the "cold start" assumption). Planned next step: Playwright automation to remove the last variance source, human click timing.
- Automated image-pipeline benchmark (2026-08, `tests/benchmark/`, see [docs/BENCHMARK.md](docs/BENCHMARK.md)) empirically confirmed a burst-drop behavior that the e2e suite never sees (single reports, `--workers=1`): a burst of ~330 consecutive input reports over the mock relay drops reports on the page side (ws dropped 30-36 on a mid-session run, nm dropped 7-37), and the FIRST burst after a cold start or data-plane switch is systematically the lossiest (ws: one report on the run right after open; nm: 21-37 reports on the first burst, losing all retries in one run). The benchmark treats a dropped report as an invalidated run and retries it, plus runs an unmeasured warm-up burst (no painting, page shows "Warming up...") at the start of each cold-start spec (benchmark-ws.spec.ts / benchmark-nm.spec.ts), which absorbs the first-burst losses and leaves the measured runs clean. The two modes are separate specs in separate workers, so both cold-start identically. Do not extrapolate from this to "WS/NM drops under normal use": the e2e suite at its normal report rate is drop-free.
- Hung-ack root cause (2026-08): the "sendReport hangs forever" class was a real addon bug, not just benchmark flake. The data worker (`addon/js/content/isolated/worker/index.js`) kept in-flight send promises in its `pending` map and only notified the bridge (`{type:'closed'}`) when the WS dropped, never settling the promises, so any connection drop left the page's sendReport pending forever. Fixed: `onClosed` now rejects and clears all pending entries, so a dropped connection surfaces as a fast `'ws closed'` rejection and the page retries (the transport reconnects on its own backoff). Verified with the e2e suite (19/19) and the benchmark. Separate benchmark-side note: the warm-up primes with an awaited 128-report burst, time-boxed per send; a fire-and-forget variant (returning after a 4-report confirmation) caused run #1 to wait behind the still-in-flight prime reports, inflating the ws total by ~2s, and a single global gate on the whole prime falsely failed slow-but-working primes under machine load. Both are pitfalls to avoid in any future warm-up redesign.
- Exploratory branches, explicitly curiosity-driven rather than requirement-driven (don't assume these were benchmark-justified):
  - **WebTransport/QUIC data-plane**: `dataPlane: "wt"` is a working third transport alongside `ws`/`nm`. The daemon starts a WT server at boot (self-signed ECDSA P-256 cert, SAN 127.0.0.1, at most 14-day validity, pinned via `serverCertificateHashes`); auth reuses the WS scheme via the URL path (WebTransport has no subprotocol); one persistent bidirectional stream per session carries the existing batch/control framing with a `[len_u32 LE]` prefix per frame (WS untouched); cert renewal rotates to a fresh port with drain (old connections keep serving, new ones get 404, the old port is released when its active sessions hit zero). Covered by `tests/e2e/wt.spec.ts` (open, input reports, sendReport/feature, no NM double-send, live ws to wt switch, rotation+drain) and `tests/benchmark/benchmark-wt.spec.ts`. Benchmark (2026-08-02, `BENCHMARK_RUNS=10`): per-report p50 0.85ms vs ws 0.78ms and nm 1.77ms (walltime p50 397ms vs ws 333ms and nm 862ms), so the TLS/QUIC encryption cost on loopback is about +0.07ms per report and WT is effectively a free security option (local-process impersonation defense via the pinned cert hash); ws remains the fastest Firefox path. Two gotchas learned: (1) Playwright `context.route` interception stalls page-main WebTransport connections (Juggler's service-worker-style intercept API cannot carry a WebTransport session); the harness no longer installs a catch-all route, so in-page WT tests run directly, but if a catch-all `context.route('**/*')` is ever reintroduced in `tests/helpers/e2e.ts`, expect the in-page WT data plane to hang and fall back to NM while workers keep working; (2) the hardening seccomp allow-list needed `SYS_fcntl` and `SYS_recvmmsg` (quinn-udp uses fcntl for O_NONBLOCK and recvmmsg for batched receive; both would have killed the hardened daemon, contradicting the old "QUIC is not blocked" assumption).
- Chromium native-WebHID benchmark added (2026-08, `chromium-benchmark` project), now fully automated and headless: WebHID cannot be granted via CDP on Chromium (`Browser.grantPermissions` rejects `hid`; the `DeviceAccess` domain does not cover the WebHID chooser, and headless requestDevice auto-resolves empty), so the mock is pre-granted with the `WebHidAllowDevicesForUrls` policy and the benchmark's `getDevices()`-based `open()` skips the chooser entirely. Three hard-won launch gotchas: (a) the policy matches origins including the port, so the benchmark serves on the fixed port 8123 and the policy file must contain exactly `http://localhost:8123`; (b) Playwright's default `headless: true` runs `chrome-headless-shell`, which has no udev/HID layer, so Chrome never enumerates the uhid mock; `channel: 'chromium'` forces the full Chrome for Testing binary in new headless mode where enumeration works; (c) `--no-sandbox` also breaks the udev enumeration, never pass it. Two findings worth keeping: (1) `vendor.bin`'s report ID 1 used to sit _between_ the two top-level collections, which Chromium's HID parser does not carry across a collection boundary (it parsed the vendor reports as unnumbered, and native `sendReport(1, ...)` failed with "Failed to write the report"); the ID now lives inside the vendor collection, and the daemon/hidreport and e2e suite (19/19) are unaffected. (2) Per the WebHID spec, `HIDInputReportEvent.data` excludes the report ID byte, so Chromium native and the polyfill deliver identical framing and the benchmark page runs unchanged. Chromium native per-report p50 was ~0.3-0.4ms in the first run (vs ~0.85ms Firefox ws, ~2ms Firefox nm), so do not read "polyfill faster than native Chromium" from any Firefox number; the polyfill-vs-native comparison still needs the Chromium testbed approach from the exploratory-branch note. (3) Chromium's `performance.now()` is coarsened to 100us by default and there is no flag to disable that clamp (crbug 438389473, still open); the benchmark page is served with COOP/COEP headers (`tests/serve.ts`) so it is cross-origin-isolated and gets 5us precision, matching the Firefox project's `privacy.reduceTimerPrecision: false`. The headers apply to the Firefox benchmark page too, which is harmless.
  - **Chromium testbed**: overriding `navigator.hid` via `Object.defineProperty` on Chromium (confirmed technically works) to compare the polyfill against Chromium's native WebHID on the same browser engine, isolating "polyfill tax" from Gecko-vs-Blink engine differences. Not yet benchmarked as of this writing (still at the "about to start measuring" stage). Do not assume or repeat any claim that the polyfill beats native Chromium until real numbers exist.

## Not every change needs a benchmark-driven justification

Some architecture changes in this project were made because they were interesting to try, not because a benchmark demanded them (e.g. binary-packed collections, WebTransport exploration). That's a legitimate reason on its own. When reviewing history here, don't retroactively invent a performance rationale for a change that was actually curiosity-driven; note it as such instead.

## Writing style: no em-dashes

Don't use em-dashes ("—") anywhere in this document or in any writing produced for this project. Rewrite with smoother sentence flow (subordinate clauses, "since"/"so"/"which", or splitting into two sentences), or fall back to a comma, colon, semicolon, or parentheses when a harder break is actually needed. Em-dash is a style tic to actively avoid, not just deprioritize.
